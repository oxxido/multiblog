# Slice 11 — Diseño propio para el admin

> Desglose accionable de `docs/PLAN.md` §S11. Aplica el sistema visual que
> S4 le dio al sitio público (`docs/Design.md`, `public/css/site.css`) al
> panel de administración, siguiendo el mockup aprobado
> `docs/UI_mockups/Divermente Admin.html`. Es una slice visual, no
> funcional: ninguna ruta, ningún campo de formulario ni ninguna
> funcionalidad de S2-S10 cambia de comportamiento, sólo de aspecto y de
> disposición en la página.

---

## 0. Decisiones tomadas para esta slice

**El mockup es de un prototipo React con 7 pantallas fijas, no una app real.**
Extraído y auditado antes de este desglose: `login`, `posts`, `editor`,
`categorias`, `medios`, `espacios`, `central`. Sólo login, posts y el editor
están resueltos con detalle real; las otras tres son listas mínimas que el
propio mockup marca como *"pantalla resuelta en versión corta: el detalle de
esta sección no entra en esta maqueta"*. Esta slice aplica el sistema visual
a las siete, pero sólo *reestiliza* las tres cortas — no les agrega
funcionalidad ni pantallas que el mockup nunca diseñó (alta de categoría ya
existe desde S3, por ejemplo, y sigue como está, sólo con la ropa nueva).

**`public/css/admin.css` es independiente de `public/css/site.css`.**
Aunque usan la misma paleta y tipografía (`Design.md` §1: fondo `#f2f2f3`,
tinta `#1d1f20`, Barlow/Barlow Condensed — son, de hecho, los mismos valores
que ya trae `site.css`), no se factoriza un archivo de tokens compartido.
`site.css` es, por decisión de S4, *"la única implementación"* de
`Design.md` para el sitio público — tocar su estructura para extraerle
tokens comunes es un cambio a una slice ya cerrada, fuera de lo que pide
esta. Se acepta la duplicación de un puñado de custom properties.

**Tipografía: Google Fonts por `<link>`, igual que S4 decidió para el sitio
público** (mismas dos familias, Barlow y Barlow Condensed — el admin no
necesita Literata, es tipografía de lectura de post, no de interfaz). Mismo
trade-off ya aceptado: una petición externa más, no rompe el invariante 3
(que además sólo rige para el sitio público, no para `/admin`).

**El admin ya tenía JavaScript (S5-S7): esta slice no lo introduce, lo
extiende con criterio.** TipTap, autosave, el picker de medios en ventana
propia (`window.open` + `postMessage`) y el alternador visual/Markdown ya
existían. Se mantienen tal cual funcionan — el alternador pasa de cambiar el
texto de un botón a mostrar dos etiquetas fijas con la activa resaltada por
CSS según `data-mode` (mismo atributo, mismo botón, `editor.ts` pierde sólo
la línea que reescribía `textContent`). El picker de medios **sigue siendo
una ventana propia, no un modal en la página**: el mockup lo muestra como
diálogo centrado, pero convertir el flujo `window.open`/`postMessage` a un
`<dialog>` en la misma página es un cambio de arquitectura de esa
funcionalidad, no de aspecto, y no lo pide ningún criterio de aceptación de
S7. Se reestiliza el contenido de `picker.eta` (grilla con marcos
`.blueprint`), no su mecánica.

**Alta rápida: dos puntos de entrada, un solo endpoint.** El mockup resuelve
"nuevo post" como un panel que se expande en la propia lista (sin ruta
nueva). Esa disposición se implementa con un `<details>` (nativo, sin JS) en
`posts/list.eta`, con el mismo formulario y el mismo `POST /admin/posts` que
ya usa `posts/new.eta`. **No se borra `GET/admin/posts/new`**: el test de
aceptación de S5 (`tests/acceptance/s5.test.ts`) verifica explícitamente que
esa pantalla exista y no pida cuerpo — seguir cumpliéndolo es más importante
que evitar una duplicación de cuatro campos. `new.eta` se reestiliza con el
mismo layout de página que el resto del admin y queda como acceso directo.

**La navegación activa se calcula del path, no se pasa desde cada ruta.**
`admin-head.eta` recibe `currentPath` (inyectado una sola vez, ver más
abajo) y decide qué ítem del menú marcar por prefijo
(`/admin/categorias`, `/admin/media`, `/admin/espacios`, `/admin/sitio`; todo
lo demás es "posts", incluido el editor). Evita tocar los ~15 manejadores de
ruta del admin sólo para decorar el menú.

**La lista de espacios activos del pie del sidebar se inyecta una sola vez,
vía `reply.locals`.** `@fastify/view` mezcla `reply.locals` con los datos de
cada `reply.view()` (`Object.assign({}, defaultCtx, this.locals, data)`). Se
agrega un `onRequest` al scope protegido de `src/routes/admin/index.ts` que
llena `reply.locals` con `activeSpaces` (id, nombre, color de acento — función
nueva, `listActiveSpacesForNav`) y `currentPath`; así ninguna ruta individual
necesita pedir esa lista para poder dibujar el sidebar. La query es la misma
tabla `spaces` que ya usa `listActiveSpaceOptions`, sin espacios archivados,
sin límite adicional al que ya usan las demás listas del admin.

**Los puntos de color del listado de posts necesitan `accentColor` del
espacio.** `listPosts()` (S2) hace `innerJoin` con `spaces` pero no
selecciona `accentColor`; se agrega esa columna al `select` existente (sin
tocar la forma de la consulta) y se suma a `PostSummary`.

**Los contadores del encabezado de Posts ("N en total · N borradores · N
programados") se calculan en memoria sobre lo que ya devuelve `listPosts()`**,
no con `COUNT(*)` nuevos — mismo criterio que S4 aceptó para "X de Y" en la
paginación pública, pero acá no hace falta ni la consulta nueva: el límite de
`listPosts()` (`LIST_LIMIT`) ya acota lo que se cuenta, igual que ya acota lo
que se lista.

**Lo que el mockup insinúa y esta slice no construye:** cabecera editorial
para "Sitio central" (titular/bajada/pie de foto — `site_settings` sólo
tiene `cover_media_id`, agregar esos campos es una migración, fuera de una
slice visual); filtros o paginación en la lista de posts (el mockup no los
diseña, y ninguna slice anterior los pidió para el admin); confirmación de
borrado con diálogo (hoy "Borrar" es un `<form>` que postea directo — se
mantiene así, sólo reestilizado; agregar una pantalla de confirmación es
funcional, no visual, y el admin ya tiene ese patrón para medios sin
uno para posts/espacios/categorías, así que no es una omisión de esta
slice sino consistencia con lo que ya había).

---

## 1. Qué prueba esta slice

Que el admin deja de ser HTML sin estilo y pasa a compartir el sistema
visual del sitio público — mismos tokens, misma familia tipográfica, mismo
lenguaje de marcos `.blueprint` — sin que ninguna de las funcionalidades
construidas en S2-S10 (CRUD de posts/espacios/categorías/medios, editor
visual con bloques ricos, autosave, portadas, programación, revisiones,
vista previa, traducción, importar/exportar) cambie de comportamiento.

---

## 2. Tareas

Cada tarea declara los archivos que puede tocar. Nada fuera de esa lista.

### T1 — Hoja de estilos del admin

Tokens (los mismos valores de color/tipografía que `Design.md` §1, ver
decisión de más arriba), reset, y componentes: `.btn`/`.btn-primary`/
`.btn-secondary`/`.btn-danger`, `.field`/`.input`/`select`/`textarea`,
`.table`, `.badge-draft`/`.badge-published`/`.badge-scheduled`, `.banner`/
`.banner-warning`/`.banner-error`, `.blueprint`+`.corner` (mismo patrón que
`site.css`, copiado — no importado, ver decisión), `.kicker`, `.card`,
`.editor-toggle` (segmentado por `data-mode`), `.space-dot`, layout
`.admin-shell`/`.admin-sidebar`/`.admin-main`, y las clases específicas de
login (`.login-shell`) y del editor de post (`.editor-grid`).

**Archivos:** `public/css/admin.css` (nuevo).

### T2 — Contexto compartido del admin (sidebar, nav activa)

`onRequest` nuevo en el scope protegido: llena `reply.locals.activeSpaces`
y `reply.locals.currentPath`. `listActiveSpacesForNav` nueva en
`taxonomy/spaces.ts` (id, name, accentColor, sin archivados).

**Archivos:** `src/routes/admin/index.ts`, `src/modules/taxonomy/spaces.ts`.

### T3 — Partials de layout del admin

`admin-head.eta` (doctype, head con fuentes y `admin.css`, apertura del
shell, sidebar con marca, nav con activa calculada de `currentPath`, lista
de espacios de `activeSpaces`, "Salir") y `admin-foot.eta` (cierre del
shell, slot para `<script type="module">` opcional). Se incluyen desde cada
plantilla protegida, con el `title` de esa pantalla como parámetro. Login no
los usa (pantalla propia, sin sidebar, fuera del scope protegido).

**Archivos:** `src/views/partials/admin-head.eta` (nuevo),
`src/views/partials/admin-foot.eta` (nuevo).

### T4 — Login

Tarjeta centrada con marcos `.blueprint`, banner de error, copy de pie
("Un solo autor. Sin registro ni recuperación."). No usa `admin-head`/
`admin-foot` (sin sidebar).

**Archivos:** `src/views/admin/login.eta`.

### T5 — Lista de posts + alta rápida

Encabezado con contadores (T de PostSummary/`accentColor`, calculados en la
ruta). Tabla con punto de color por espacio, badges de estado, fecha
formateada. `<details>` de alta rápida con los mismos cuatro campos que
`posts/new.eta`, mismo `POST /admin/posts`. `posts/new.eta` se reestiliza
con el layout compartido, sin cambiar su formulario ni su ruta.

**Archivos:** `src/views/admin/posts/list.eta`, `src/views/admin/posts/new.eta`,
`src/routes/admin/posts.ts` (contadores en el `GET /`), `src/modules/content/posts.ts`
(`accentColor` en `PostSummary`/`listPosts`).

### T6 — Editor de post

Barra superior (volver, estado, idioma, hermano, vista previa, rotar token,
historial) con el filete del color del espacio. Banner de traducción
desactualizada. Grilla de dos columnas: formulario principal (con la barra
de herramientas del editor visual ya existente, alternador segmentado) +
sidebar de publicación (Guardar/Publicar/Programar/Portada/Categorías/Tags/
Traducir/Borrar) — todos los `<form>` que ya existen, reordenados y
reestilizados, ninguno nuevo. `editor.ts` pierde la línea que reescribe
`textContent` del alternador (pasa a resolverse por CSS con `data-mode`).

**Archivos:** `src/views/admin/posts/form.eta`, `src/admin-client/editor.ts`.

### T7 — Historial y diff de revisiones

Mismo layout compartido, lista de revisiones y bloque de diff reestilizados
(colores de inserción/borrado con los tokens nuevos en vez del `<style>`
inline actual).

**Archivos:** `src/views/admin/posts/revisions.eta`,
`src/views/admin/posts/revision-diff.eta`.

### T8 — Categorías, medios, espacios

Las tres pantallas "cortas": listas con el layout compartido y tabla/lista
del sistema nuevo, formularios (categoría, espacio) con los mismos campos,
picker y confirmación de borrado de medios con marcos `.blueprint` en las
miniaturas. Ninguna gana campos ni pasos nuevos.

**Archivos:** `src/views/admin/categories/list.eta`,
`src/views/admin/categories/form.eta`, `src/views/admin/media/list.eta`,
`src/views/admin/media/confirm-delete.eta`, `src/views/admin/media/picker.eta`,
`src/views/admin/spaces/list.eta`, `src/views/admin/spaces/form.eta`,
`src/views/partials/cover-field.eta` (sólo clases, mismo marcado/atributos
`data-*`).

### T9 — Sitio central

Formulario de portada reestilizado con el layout compartido y el campo de
portada existente (`cover-field`). Sin titular/bajada/pie de foto (ver
decisión §0 — eso es una migración, no esta slice).

**Archivos:** `src/views/admin/site/form.eta`.

### T10 — Test de aceptación

`tests/acceptance/s11.test.ts`: cada una de las siete pantallas responde 200
autenticado y usa `admin.css`; el alta rápida desde la lista crea un post
(mismo `POST /admin/posts` que ya prueba S5); el badge de un post programado
difiere del de uno publicado y del de un borrador; la nav marca "Categorías"
activa en `/admin/categorias` y "Posts" en `/admin/posts/{id}` (el editor);
ninguna plantilla de admin quedó rota (títulos, formularios con los mismos
`name` que antes, para no romper los tests existentes que dependen de esos
atributos).

**Archivos:** `tests/acceptance/s11.test.ts` (nuevo).

## 3. WON'T DO

```text
comentarios
usuarios múltiples y roles
newsletter
analytics propio
temas intercambiables por UI
sistema de plugins
búsqueda full-text
traducciones de contenido
```

Tampoco, específico de S11: cabecera editorial de "Sitio central"
(titular/bajada/pie de foto — requiere migración); filtros o paginación en
la lista de posts; confirmación con diálogo para borrar post/espacio/
categoría; convertir el picker de medios en un `<dialog>` de la misma
página; factorizar tokens compartidos entre `site.css` y `admin.css`;
cualquier cambio de esquema, de rutas públicas o del pipeline de Markdown.

---

## 4. Criterio de aceptación

```text
✓ login, posts, editor de post, historial/diff, categorías, medios, espacios
  y sitio central usan public/css/admin.css y el layout compartido
  (admin-head/admin-foot)
✓ el punto de color por espacio, los badges de estado y los marcos
  .blueprint aparecen donde el mockup los muestra
✓ ninguna ruta cambia de URL ni de método; ningún formulario pierde ni gana
  campos fuera de lo descripto en §0
✓ el alternador visual/Markdown, el autosave, el picker de medios, la
  programación, las revisiones, la vista previa y la traducción siguen
  funcionando igual que antes de esta slice
✓ pnpm lint && pnpm typecheck && pnpm test en verde
```
