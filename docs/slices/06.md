## 0. Decisiones tomadas para esta slice

**El registro de `SPEC.md` §3 se implementa con un `render` que produce
`hast`, no el string HTML que sugiere el pseudocódigo.** El pseudocódigo del
spec dice `render: (node, attrs) => string`. En la práctica, `remark-rehype`
ya está en `src/markdown/pipeline.ts` (S1) y convierte todo el árbol
`mdast → hast` antes de `rehype-sanitize` y `rehype-stringify`; devolver un
string HTML desde un bloque individual obligaría a parsearlo de nuevo para
poder sanearlo junto con el resto del documento, o a sanearlo aparte del
resto (dos pasadas de saneado en vez de una, invariante 4 en riesgo). En
cambio, cada bloque registra un **handler de `mdast-util-to-hast`**
(`(state, node) => hast.Element`, la firma que ya usa esa librería para
convertir cualquier nodo), pasado a `remarkRehype` vía su opción
`handlers`. Esto es una sola pasada de saneado para todo el documento, y le
da a cada bloque `state.all(node)` para convertir sus hijos de Markdown
normal (párrafos, imágenes) recursivamente sin reimplementar esa lógica. La
forma pública del registro (nombre, `attrs` con Zod, un nodo TipTap, ida y
vuelta a Markdown) es la misma que describe `SPEC.md` — cambia el tipo de
`render`, no el contrato que ve quien agrega un bloque nuevo.

**Mapeo bloque → tipo de directiva, fijo por bloque, no elegible:**

```text
callout  → containerDirective   :::callout{type=warning} … :::
gallery  → containerDirective   :::gallery{cols=3} … :::
youtube  → leafDirective        ::youtube[dQw4w9WgXcQ]
```

`callout` y `gallery` necesitan contenido anidado (párrafos e imágenes), lo
que en `remark-directive` es exclusivamente `containerDirective` (`:::`).
`youtube` no tiene contenido, sólo un identificador y atributos — eso es
`leafDirective` (`::`), como ya anticipaba el ejemplo de `SPEC.md` §3. El
registro no declara este tipo por bloque como configuración libre: el
motor tiene un handler fijo por cada uno de los tres tipos de directiva de
`remark-directive` (`containerDirective`, `leafDirective`, `textDirective` —
este último sin uso todavía, ningún bloque de esta slice es en línea) que
busca el nombre del nodo en el registro y delega. Añadir un bloque
`containerDirective` o `leafDirective` nuevo no toca el motor, tal como pide
`PLAN.md`; añadir un bloque `textDirective` sí tocaría el motor (agregar ese
tercer handler) — no hace falta en esta slice, se anota para cuando haga
falta.

**Atributos de cada bloque, validados con Zod en el borde (la convención ya
fijada en `CLAUDE.md`) antes de renderizar:**

```ts
callout: { type: z.enum(["info", "warning", "success"]).default("info") }
gallery: { cols: z.coerce.number().min(1).max(4).default(2) }
youtube: { title: z.string().trim().min(1).default("Video de YouTube") }
```

Un atributo que no valida (`cols=9`, `type=peligro`) no rompe el render del
resto del post: el bloque cae a sus valores por defecto y el post se sigue
publicando — coherente con que Markdown mal escrito en cualquier otro lado
(un enlace roto, una tabla desalineada) tampoco tira abajo la petición.

**`youtube` embebe con `<iframe>` a `youtube-nocookie.com`, sin script
propio.** El invariante 3 dice cero JavaScript en el sitio público — un
`<iframe>` es HTML, no JS nuestro; lo que corra dentro de ese documento
embebido es de YouTube, no un byte que este servidor emita. Se usa el
dominio `-nocookie` (no pone cookies de seguimiento hasta que el visitante
interactúa) y `loading="lazy"` porque son atributos HTML planos, no
comportamiento agregado por nosotros. El `title` (atributo de accesibilidad
obligatorio en un iframe, no relacionado con el atributo Markdown del mismo
nombre salvo que lo alimenta) usa el `title` validado arriba.

**CSS de `.youtube-embed`, nuevo — `Design.md` no lo cubre.** El diseño
aprobado (`Design.md` §3.6) documenta `callout`, `gallery` y `code`, pero no
un tercer bloque rico de video: el video no estaba en el mockup porque
`PLAN.md` fijó `youtube` recién al planificar esta slice, después de
`Design.md`. Se sigue el mismo lenguaje visual que los otros dos (ancho de
columna, sin decoración extra): contenedor `max-width: 640px` (el ancho de
columna del cuerpo, igual que `callout`), proporción 16:9 con
`aspect-ratio`, sin marco `.blueprint` (ese marco es para fotografías
propias — S7 —, no para un embed de terceros). No es una entrada en
`DECISIONS.md`: es una precisión de estilo dentro del alcance ya aprobado,
del mismo tipo que las que S4 dejó anotadas sin escalar (ancho del
contenedor, copy del header).

**El pie de cada imagen de `gallery` es su propio `alt`, no una sintaxis de
caption nueva.** `Design.md` dice "retícula de marcos `.blueprint` en 4:3,
con pie debajo" sin especificar de dónde sale el texto del pie. Inventar una
sintaxis de caption (`![alt](src "caption")` usando el `title` de Markdown,
o un atributo por imagen) agrega superficie al formato para un problema que
ya tiene solución: el `alt` que el autor ya escribe para cada imagen
(`![Alt uno](/media/a.jpg)`, el ejemplo del propio `SPEC.md`) es el pie. Si
el `alt` viene vacío, ese marco no lleva `<figcaption>` — sigue siendo
accesible (un `alt=""` vacío es válido para imagen decorativa) y no imprime
un pie vacío.

**`gallery` no depende de que exista media (S7).** El bloque acepta
cualquier URL de imagen en el `src` de Markdown estándar, igual que ya
acepta el pipeline hoy para una imagen suelta fuera de un bloque. No hay
biblioteca de medios, subida ni recorte todavía — eso sigue siendo S7,
íntegro. Esta slice sólo agrupa imágenes ya referenciables en una retícula
con clase `.gallery`; el día que exista S7, insertar una imagen de la
biblioteca dentro de un `gallery` es sólo escribir su URL, sin cambios acá.

**Nodo TipTap por bloque, sin editar contenido rico dentro de `gallery` ni
`youtube`.** Los tres son nodos de bloque (`group: "block"`) en el esquema
de `src/markdown/tiptap/extensions.ts`, pero con dos formas distintas:

- `callout` — `content: "paragraph+"`, como una cita: el usuario edita
  párrafos normales adentro del bloque, con un selector del `type` en la
  barra de herramientas de ese nodo (NodeView con un `<select>` propio).
  Esto reutiliza directamente el `paragraph` que T1 de S5 ya convierte —
  ningún tipo de nodo nuevo dentro del contenido.
- `gallery` — nodo átomo (`atom: true`, sin contenido editable), con un
  atributo `images: { src: string; alt: string }[]` y `cols: number`. Se
  edita con un prompt (ver T4): pegar una URL por línea, con `alt`
  opcional separado por `|`. No hay UI de arrastrar-y-soltar ni de
  reordenar — eso es exactamente lo que traería una biblioteca de medios
  (S7); acá alcanza con texto porque no hay archivos que administrar
  todavía.
- `youtube` — nodo átomo, atributos `videoId: string` y `title: string`.
  En el editor se muestra como una tarjeta de vista previa con el id y un
  enlace a `https://www.youtube.com/watch?v={id}` (para que el autor pueda
  verificar qué video es sin cargar un iframe de YouTube dentro del propio
  editor — evita meterle a la superficie de edición un documento de
  terceros que no controlamos).

**Barra de inserción: extiende la barra de T4 de S5, con `window.prompt`
para los atributos.** S5 no dejó una barra de herramientas todavía (el
único control era el toggle visual/crudo); esta slice agrega la primera. No
hay formularios ni modales nuevos: como el admin no está sujeto al
invariante 3, tres botones ("Callout", "Galería", "YouTube") que abren
`window.prompt()` para pedir lo mínimo (tipo de callout con valor por
defecto; URLs de imágenes para galería; id o URL completa de YouTube, se
acepta cualquiera de las dos formas y se extrae el id con una expresión
regular) resuelven la inserción sin construir UI dedicada — coherente con
que el resto del admin de S2/S3 tampoco tiene componentes propios más allá
de formularios HTML planos. Un modal con campos propios queda para si esto
resulta insuficiente en el uso real; no se construye por adelantado.

**El bloque de código con cerca (```` ``` ````) no es parte de esta
slice, aunque `Design.md` §3.6 lo mencione junto a `callout`/`gallery`.**
`PLAN.md` fija los tres bloques de S6 explícitamente: `callout`, `gallery`,
`youtube`. El código con cerca ya se renderiza desde S1 (pipeline
`remark → rehype-shiki → sanitize`), no es una directiva ni pasa por el
registro — es Markdown estándar. La clase `.code-block` que ya existe en
`public/css/site.css` (S4, sin uso real) no envuelve hoy la salida de Shiki
(`<pre class="shiki">…`), así que ese hairline visual sigue sin aplicarse
después de esta slice también. Es un gap real de `Design.md` §3.6, pero
aplicarlo es tocar el pipeline de código fuente (envolver la salida de
Shiki en el contenedor), no el registro de bloques — se deja anotado para
decidir con el usuario si entra en S6 o en una slice de ajuste visual
aparte, no se decide unilateralmente acá.

**Cómo se prueba el round-trip.** Igual que S5: `tests/roundtrip/` llama
directo a `fromMarkdown`/`toMarkdown` con un archivo por bloque. La
extensión de esos dos conversores para reconocer directivas usa el mismo
registro que el pipeline público — un bloque nuevo que registra su
conversión no toca `fromMarkdown.ts` ni `toMarkdown.ts`, sólo agrega una
entrada.

## 1. Qué prueba esta slice

Del plan: que el "techo de riqueza lo pone el registro de bloques, no el
formato" (`SPEC.md` §3) es cierto en código, no sólo en la promesa de
diseño. Prueba que `remark-directive` conviven con el resto del pipeline
(saneado incluido — invariante 4, un bloque no es una forma de colarse
HTML sin sanear) y que la garantía de round-trip que S5 estableció para los
nodos base también vale para contenido con bloques: escribir un post con
los tres bloques, guardarlo, y que tanto el Markdown crudo como el
documento del editor visual sobrevivan intactos.

## 2. Tareas

Cada tarea declara los archivos que puede tocar. Nada fuera de esa lista.

### T1 — Registro de bloques y handlers de `mdast-util-to-hast`

El núcleo del motor: el tipo `BlockDefinition` (nombre, `attrs` con Zod, el
handler de conversión a `hast`, el nodo TipTap, la conversión a Markdown) y
los tres handlers genéricos por tipo de directiva
(`containerDirective`/`leafDirective`/`textDirective`) que buscan el nombre
en el registro y delegan — sin bloques todavía, este archivo puede probarse
con un registro vacío. `src/markdown/pipeline.ts` pasa esos tres handlers a
`remarkRehype` vía su opción `handlers`, junto a los del set por defecto de
`mdast-util-to-hast` (`defaultHandlers`, para que párrafos/imágenes/etc.
sigan convirtiendo igual).

**Archivos:** `src/markdown/blocks/types.ts` (nuevo, `BlockDefinition` y el
tipo de handler), `src/markdown/blocks/registry.ts` (nuevo, mapa vacío +
función `registerBlock`), `src/markdown/blocks/toHast.ts` (nuevo, los tres
handlers genéricos), `src/markdown/pipeline.ts` (pasa `handlers` a
`remarkRehype`).

### T2 — Bloque `callout`

Primera entrada real del registro. `render` construye un `<div
class="callout callout--{type}">` con un `<p class="callout__label">`
(según el `type`, ver T5 de copy) y el resto de los hijos convertidos vía
`state.all(node)`. Nodo TipTap con `content: "paragraph+"` y atributo
`type`.

**Archivos:** `src/markdown/blocks/callout.ts` (nuevo: attrs, handler
hast, nodo TipTap, `toMarkdown`), `src/markdown/blocks/index.ts` (nuevo,
registra los tres bloques de esta slice — único punto de entrada que
importa `src/markdown/tiptap/extensions.ts` y `src/markdown/pipeline.ts`),
`src/markdown/tiptap/extensions.ts` (suma el nodo de `callout` a la lista),
`src/markdown/tiptap/fromMarkdown.ts` / `toMarkdown.ts` (reconocen
`containerDirective` con `name === "callout"`, delegando al registro en vez
de a una lista de casos cableada a mano — mismo principio que T1).

### T3 — Bloques `gallery` y `youtube`

Mismo patrón que T2, dos bloques más. `gallery` extrae las imágenes de sus
hijos (ignora los `<p>` que las envuelven, es el resultado normal de que
Markdown ponga cada `![]()` suelto en su propio párrafo) y arma
`.gallery > .gallery__grid > .blueprint.gallery__frame` con `<img>` +
`<figcaption>` opcional (según alt, §0). `youtube` no tiene hijos: valida
`videoId` (viene del `label` de la directiva, `::youtube[id]`, no de un
atributo) y arma el `<iframe>` a `youtube-nocookie.com`.

**Archivos:** `src/markdown/blocks/gallery.ts` (nuevo), `src/markdown/blocks/youtube.ts`
(nuevo), `src/markdown/blocks/index.ts`, `src/markdown/tiptap/extensions.ts`,
`src/markdown/tiptap/fromMarkdown.ts`, `src/markdown/tiptap/toMarkdown.ts`,
`public/css/site.css` (agrega `.youtube-embed`, §0 — `.callout`, `.gallery`
y sus clases hijas ya existen desde S4).

### T4 — Barra de inserción en el editor

Tres botones nuevos sobre el editor de S5 (`src/admin-client/editor.ts`),
cada uno arma el `attrs`/contenido del bloque a partir de lo que devuelve
`window.prompt()` (§0: validación mínima en cliente — vacío o cancelado no
inserta nada; la validación real sigue siendo la de Zod en el registro, del
lado servidor, al guardar) y ejecuta el comando TipTap correspondiente
(`insertContent` con el nodo ya armado). Las NodeViews de los tres bloques
(vista de `callout` con selector de `type`, tarjeta de `gallery` con
miniaturas simples, tarjeta de `youtube` con el enlace de verificación) se
definen acá porque son las únicas piezas de esta slice que corren en el
navegador, no en el conversor.

**Archivos:** `src/admin-client/editor.ts`, `src/views/admin/posts/form.eta`
(el contenedor de la barra, si hace falta marcado nuevo).

### T5 — Tests de round-trip

Un archivo por bloque, mismo criterio que T2 de S5: `markdown →
fromMarkdown → toMarkdown` debe devolver el Markdown de entrada o su forma
canónica documentada como tal.

**Archivos:** `tests/roundtrip/callout.test.ts`,
`tests/roundtrip/gallery.test.ts`, `tests/roundtrip/youtube.test.ts`
(todos nuevos).

### T6 — Aceptación de punta a punta

Post con los tres bloques, publicado, servido en su subdominio: el HTML
resultante tiene las clases/elementos esperados (`.callout--warning`,
`.gallery__grid` con el número de columnas pedido, `<iframe
src="https://www.youtube-nocookie.com/embed/...">`) y sigue pasando por
`rehype-sanitize` (un atributo o tag fuera del esquema saneado no aparece,
verificado con un bloque que intenta colar `onerror=` en un `alt`, por
ejemplo). Confirma también que un atributo inválido (`cols=9`) no rompe el
render del resto del post.

**Archivos:** `tests/acceptance/s6.test.ts` (nuevo).

## 3. WON'T DO

Recordatorio para cualquier tarea de esta slice — no se construye nada de
esto todavía, aunque parezca dos líneas:

```text
comentarios
usuarios múltiples y roles
newsletter
analytics propio

```

Tampoco, específico de S6: un cuarto bloque más allá de los tres del plan,
biblioteca de medios o subida de imágenes (S7 — `gallery` sólo agrupa URLs
ya existentes), sintaxis de caption distinta del `alt` de la imagen,
reordenar o editar imágenes de una `gallery` con drag-and-drop, vista previa
real (iframe embebido) de `youtube` dentro del propio editor, bloques
`textDirective` (en línea), envolver la salida de Shiki en `.code-block`
(gap real de `Design.md` §3.6, ver §0 — a decidir aparte, no en esta
slice), historial de revisiones (S9).

## 4. Criterio de aceptación

```text
✓ los tres bloques se insertan desde el editor visual y se renderizan
  correctamente en el sitio público, con las clases de Design.md/§0
✓ los tres sobreviven md → editor → md idénticos (o su forma canónica
  documentada, test de round-trip por bloque)
✓ un cuarto bloque hipotético sólo agrega una entrada al registro
  (src/markdown/blocks/index.ts) y sus dos archivos de conversión — no
  toca pipeline.ts, toHast.ts ni fromMarkdown.ts/toMarkdown.ts
✓ un atributo inválido en un bloque cae a su valor por defecto sin romper
  el resto del post
✓ todo el HTML de los tres bloques sigue pasando por rehype-sanitize
  (invariante 4): un intento de inyección dentro de un bloque no sobrevive
✓ corriendo en esta máquina vía docker compose (app + caddy + postgres),
  gestionado por dockge
✓ pnpm lint && pnpm typecheck && pnpm test en verde
```
