## 0. Decisiones tomadas para esta slice

Cuatro decisiones de arquitectura se consultaron con el usuario antes de
escribir este desglose (tocan el modelo de datos o suman dependencia al
stack cerrado). Quedan también en `docs/DECISIONS.md` D17.

**Publicación programada: job periódico en el mismo proceso, no filtro en
tiempo de consulta — confirmado con el usuario.** La alternativa (tratar un
post `scheduled` con `published_at <= now()` como públicamente visible sin
tocar la columna) evitaba sumar un timer, pero el usuario prefirió que
`status` sea siempre la fuente de verdad exacta de lo que un post "es" en
cada momento, aunque eso implique una ventana de latencia igual al
intervalo del job. `src/modules/content/scheduler.ts` (nuevo) expone
`publishDuePosts(): Promise<number>` — `UPDATE posts SET status =
'published', published_at = published_at WHERE status = 'scheduled' AND
published_at <= now()`, sin tocar `published_at` (ya tiene la fecha
programada, que pasa a ser la fecha real de publicación) — y
`startScheduledPublishJob(intervalMs = 60_000): () => void`, que llama a
`publishDuePosts()` cada minuto y devuelve una función para detenerlo.
`publishDuePosts` se prueba llamándola directamente (sin el timer), mismo
criterio que S8 mockea `fetch` en vez de llamar a OpenRouter de verdad: un
test no puede esperar un minuto real. Ninguna de las consultas públicas
existentes (`findPublishedPost`, `listPublishedPosts`,
`listLatestAcrossSpaces`, feeds, sitemaps — todas filtran ya
`status = 'published'`) necesita cambiar.

**Vista previa: token persistente en columna nueva, no HMAC efímero —
confirmado con el usuario.** `posts` gana `preview_token` (`uuid`,
`defaultRandom()`, `unique()`), sembrado en cada post desde que se crea,
igual que ya pasa con `id`. La URL es `GET /_preview/{token}` — sin prefijo
de idioma, porque el token ya identifica un post concreto con su propio
`lang`, a diferencia de las demás rutas de `space.ts` que sí distinguen
`/en/`. Sólo resuelve dentro del subdominio de un espacio (404 si
`request.space` es `null`, mismo patrón de guarda que usan hoy `/espacios`
o `/t/{tag}` al revés) y la consulta sigue filtrando por
`request.space.id` además de por el token — no porque el token sea
adivinable (es un UUID), sino porque toda consulta de contenido filtra por
`space_id` sin excepciones (invariante 2). El link se puede "rotar" desde
el admin (`POST /admin/posts/{id}/rotate-preview-token`, reemplaza el UUID
por uno nuevo), que es la única forma de invalidar uno viejo — no hay
expiración automática.

**Revisiones: una fila nueva sólo en el guardado explícito del formulario
completo, nunca en el autosave — confirmado con el usuario.** Tabla nueva
`post_revisions` (`id`, `post_id` → `posts` con `onDelete: cascade`,
`body_md`, `created_at`). `POST /admin/posts/{id}` (el que atiende
`form.eta`, no `/autosave`) llama, después de `updatePost`, a
`recordRevisionIfChanged(postId, bodyMd)`: compara contra la última
revisión guardada (o contra "ninguna" en el primer guardado real de un post
recién creado) y sólo inserta si cambió. Esto evita cientos de filas por
sesión de escritura — el autosave de S5 dispara cada 2 segundos mientras se
tipea y nunca debe generar una revisión por sí solo (`autosavePostBody`
queda intacto, sin tocar). El diff se muestra sólo **contra la revisión
inmediatamente anterior** — no hay selector de un par arbitrario de
revisiones; es lo que pide literalmente `docs/PLAN.md` ("histórico... con
diff") sin que ningún documento pida comparar versiones no consecutivas.
Dependencia nueva propuesta y confirmada: **`diff`** (diff de líneas en
texto plano, sin parsear Markdown ni HTML) — única alta al stack cerrado
para esta slice. La vista de diff escapa manualmente las entidades HTML del
Markdown crudo antes de envolverlo en `<ins>`/`<del>` (mismo criterio que
`escapeXmlText` de `rss.ts` en S9): esto nunca pasa por
`body_html`/`rehype-sanitize` porque no es el pipeline de contenido
(invariante 1/4), es una vista de depuración del propio Markdown fuente,
sólo visible en el admin.

**Import/export: scripts CLI + front-matter propio, sin dependencia nueva —
confirmado con el usuario.** `pnpm import <espacio> <directorio>` / `pnpm
export <espacio> <directorio>`, mismo patrón que `db:seed`
(`tsx --env-file-if-exists=.env.local src/scripts/{import,export}.ts`), un
espacio por invocación — nada de subida por el admin, es una operación que
el único usuario del sitio ya corre desde la terminal para migrar y
desplegar. El front-matter es `clave: valor` línea por línea entre dos
líneas `---`, sin YAML real: lo escribe y lo lee únicamente esta
herramienta, así que no hace falta un parser general (mismo espíritu que
S9 armó el XML de RSS/sitemap a mano en vez de sumar una dependencia).

Detalle del formato y del comportamiento de import/export, decisiones de
implementación que no ameritaban otra pregunta al usuario:

- **Un subdirectorio por idioma:** `{directorio}/es/{slug}.md` y
  `{directorio}/en/{slug}.md`, en vez de un campo `lang` en el
  front-matter — evita duplicar información y espeja el prefijo `/en/` que
  ya organiza el resto de las rutas públicas.
- **Campos del front-matter:** `title`, `slug`, `status`
  (`draft`/`scheduled`/`published`), `published_at` (ISO 8601, omitido si
  `status` es `draft`), `excerpt` (omitido si no hay), `categories` (slugs
  separados por coma, omitido si no hay ninguna), `tags` (nombres separados
  por coma, mismo formato que ya escribe el input de S9), `translation_of`
  (sólo en archivos de `en/`: el `slug` del archivo de `es/` del mismo lote
  del que es traducción — resuelve `source_post_id`/`translation_group_id`
  al importar; si falta, el post importa con un grupo de traducción propio,
  sin hermano). Ningún campo de portada ni de imágenes: los medios quedan
  fuera (siguiente punto).
- **Medios fuera de alcance.** El export no reconstruye `media` ni copia
  archivos del volumen — ya se respaldan con `pg_dump` + el volumen
  (`docs/SPEC.md` §8). Un post exportado y reimportado en una base vacía
  pierde su portada (`cover_media_id` queda `null`) y cualquier imagen
  suelta o de galería en el cuerpo apunta a un `/media/{id}/...` que puede
  no existir todavía — aceptado explícitamente, es el mismo tipo de límite
  que ya tiene `docs/SPEC.md` §8 para el respaldo completo del sitio.
- **Categorías deben existir antes de importar; tags se crean solos.** Un
  nombre de categoría que no exista en el espacio destino hace fallar el
  import de ese archivo (no se inventan categorías nuevas silenciosamente:
  son la estructura curada de cada blog). Los tags sí son *find-or-create*,
  reusando `syncPostTags` de S9 tal cual — ya es su comportamiento con
  cualquier post nuevo.
- **Import es upsert por `(espacio, lang, slug)`.** Si ya existe un post
  con esa clave se actualiza; si no, se crea. Así una reimportación después
  de vaciar la base y una carga incremental de archivos nuevos usan el
  mismo comando sin distinguir casos.
- **El export es completo: incluye borradores y programados, no sólo
  publicados** — es la herramienta de respaldo/portabilidad que promete
  `docs/SPEC.md` §3 y §9 ("exportás todo el blog en cualquier momento"), no
  un exportador de "lo publicado".
- **Sin reconstrucción de `post_slugs`.** El export no guarda el historial
  de slugs viejos de un post (no está en su Markdown ni en su
  front-matter); reimportar después de vaciar la base parte con el slug
  actual únicamente, sin las redirecciones 301 que existían antes de
  vaciar. Aceptado: reconstruir esas redirecciones necesitaría exportar
  también `post_slugs`, que ningún documento pide.

Ningún cambio de esquema fuera de `posts.preview_token` y la tabla
`post_revisions` — ambos cubiertos por una única migración de Drizzle.

## 1. Qué prueba esta slice

Que el flujo de escritura deja de depender de que todo pase por el
formulario de admin en el momento exacto de publicar. Un borrador se puede
mostrar a alguien sin publicarlo, un post puede quedar listo antes y salir
solo a su hora, un cambio de redacción se puede revisar contra la versión
anterior, y el contenido entero puede salir de la base y volver a entrar
sin el sitio adentro — el criterio de aceptación de `docs/SPEC.md` §9 ("todo
el contenido se puede exportar a archivos .md") pasa de ser cierto en
teoría (nunca se probó con un importador real) a demostrado con un
round-trip completo.

## 2. Tareas

Cada tarea declara los archivos que puede tocar. Nada fuera de esa lista.

### T1 — Esquema: `preview_token` y `post_revisions`

`posts` gana `previewToken: uuid("preview_token").notNull().defaultRandom().unique()`.
Tabla nueva `postRevisions`: `id` (uuid, pk, `defaultRandom()`), `postId`
(uuid, `references(() => posts.id, { onDelete: "cascade" })`), `bodyMd`
(text, not null), `createdAt` (timestamp con tz, `defaultNow()`), con
índice `(postId, createdAt)` para listar el historial de un post en orden.
Migración generada con `pnpm db:generate` y aplicada contra el Postgres de
dev.

**Archivos:** `src/db/schema.ts`, migración nueva en `src/db/migrations/`.

### T2 — Publicación programada: módulo y funciones de contenido

`src/modules/content/scheduler.ts` (nuevo): `publishDuePosts(): Promise<number>`
(cuenta de posts publicados en esa corrida) y
`startScheduledPublishJob(intervalMs = 60_000): () => void`. En
`posts.ts`: `schedulePost(id: string, publishAt: Date): Promise<void>`
(`status: "scheduled", publishedAt: publishAt`) y
`cancelSchedule(id: string): Promise<void>` (`status: "draft", publishedAt:
null`) — mismo estilo que `publishPost`, que queda intacto (sigue siendo
"publicar ya", independiente de si el post estaba programado o en
borrador). `src/server.ts` arranca el job después de que Fastify escucha
(`startScheduledPublishJob()`) y lo detiene en el hook `onClose`.

**Archivos:** `src/modules/content/scheduler.ts` (nuevo),
`src/modules/content/posts.ts`, `src/server.ts`.

### T3 — Admin: programar y cancelar desde el formulario

`editPostFormSchema` no cambia (sigue sin `status`); dos rutas nuevas en
`routes/admin/posts.ts`: `POST /:id/schedule` (`z.object({ publishAt:
z.string() })`, refinado a fecha futura — 400 si no lo es — parsea a `Date`
y llama a `schedulePost`) y `POST /:id/cancel-schedule` (llama a
`cancelSchedule`, sin body). `form.eta` gana un tercer bloque junto a
"Publicar": un `<input type="datetime-local">` con botón "Programar" (visible
siempre) y, sólo cuando `it.post.status === "scheduled"`, la fecha
programada y un botón "Cancelar programación". `list.eta` dejaba el
`status` crudo (`draft`/`scheduled`/`published`, sin traducir, confirmado al
investigar el código actual): pasa a una tabla de tres etiquetas
("Borrador"/"Programado para {fecha}"/"Publicado") en ambas plantillas —
primera vez que el admin traduce este campo, no un ajuste sobre una
traducción previa.

**Archivos:** `src/routes/admin/posts.ts`, `src/views/admin/posts/form.eta`,
`src/views/admin/posts/list.eta`.

### T4 — Vista previa por URL secreta

`createPost` no cambia (el `defaultRandom()` de la columna alcanza).
`posts.ts` gana `findPostByPreviewToken(spaceId: string, token: string):
Promise<PostDetail | null>` (filtra por `spaceId` además del token,
invariante 2) y `rotatePreviewToken(id: string): Promise<string>` (nuevo
UUID vía `sql\`gen_random_uuid()\`` en el `update`, devuelve el token
nuevo). Ruta nueva en `routes/public/space.ts`, fuera de las fábricas
`spaceIndexRoutes`/`postRoutes` (no depende de idioma): `GET
/_preview/:token`, 404 si `request.space` es `null` o si no hay match;
si hay, renderiza con la misma vista de post (`post.eta`) más un aviso fijo
arriba ("Vista previa — no es la versión pública") cuando `status !==
"published"`. Ruta nueva en `routes/admin/posts.ts`: `POST
/:id/rotate-preview-token`. `src/routes/public/urls.ts` gana
`previewUrlFor(request, space, token)`, reusado por `form.eta` (vía el
handler de `GET /admin/posts/:id`, que arma el link absoluto y se lo pasa a
la vista) para mostrar el link completo con un botón de rotar al lado.

**Archivos:** `src/modules/content/posts.ts`, `src/routes/public/space.ts`,
`src/routes/public/urls.ts`, `src/routes/admin/posts.ts`,
`src/views/admin/posts/form.eta`, `src/views/post.eta` (aviso condicional).

### T5 — Revisiones: registro y consulta

`diff` nueva dependencia (`dependencies`, no dev — se usa en una ruta de
admin, no sólo en tests). `src/modules/content/revisions.ts` (nuevo):
`recordRevisionIfChanged(postId: string, bodyMd: string): Promise<void>`,
`listRevisions(postId: string): Promise<{ id: string; createdAt: Date }[]>`
(orden descendente, `LIMIT` fijo tipo `REVISION_LIST_LIMIT = 200`, mismo
criterio que el resto de `.claude/rules/Db.md`), `getRevision(id: string):
Promise<{ id: string; postId: string; bodyMd: string; createdAt: Date } |
null>`, `diffAgainstPrevious(revisionId: string): Promise<string | null>`
(HTML del diff con `diffLines` de `diff`, `null` si es la primera revisión
del post — no hay "anterior"). El handler de `POST /admin/posts/:id` (el
del formulario completo) llama a `recordRevisionIfChanged` después de
`updatePost`, nunca el de `/autosave`.

**Archivos:** `src/modules/content/revisions.ts` (nuevo),
`src/routes/admin/posts.ts`, `package.json` (dependencia `diff`).

### T6 — Admin: historial y diff

2 aplicada también acá, aunque sea un post y no un espacio: nunca se
resuelve una revisión sin confirmar que pertenece al post de la URL). Link

**Archivos:** `src/routes/admin/posts.ts`, `src/views/admin/posts/revisions.eta`

### T7 — Front-matter: parseo y serialización puros

herramienta (no es YAML, no lo abre otro programa).

## 4. Criterio de aceptación

```text
✓ programar un post a futuro → no aparece públicamente hasta que
  publishDuePosts() lo alcanza; el job en el proceso real lo hace solo,
  sin intervención manual
✓ cancelar una programación devuelve el post a borrador
✓ un borrador (o un post programado) tiene un link de vista previa que lo
  muestra en el subdominio real con un aviso de que no es la versión
  pública; rotar el link invalida el anterior
✓ guardar el formulario de edición registra una revisión nueva de body_md
  sólo si cambió; el autosave nunca lo hace; el admin muestra el diff de
  una revisión contra la anterior
✓ importar 20 archivos .md a un espacio en una operación (pnpm import)
✓ exportar, borrar la base, reimportar → contenido equivalente (título,
  slug, estado, extracto, cuerpo, categorías, tags, grupo de traducción)
✓ corriendo en esta máquina vía docker compose, gestionado por dockge
✓ pnpm lint && pnpm typecheck && pnpm test en verde
```
