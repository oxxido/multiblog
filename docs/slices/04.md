## 0. Decisiones tomadas para esta slice

**El conversor Markdown ↔ TipTap se escribe con remark, no con una librería
de terceros.** Se evaluó `tiptap-markdown` (envuelve `prosemirror-markdown`)
y se descartó: correría un serializador de Markdown distinto al que ya usa
`src/markdown/pipeline.ts` para `body_html`, con riesgo de que el editor
visual escriba un Markdown con estilo levemente distinto (viñetas, énfasis)
al que produciría el pipeline público, y no sabe nada de `remark-directive`
— la fricción quedaría para S5. En cambio, `src/markdown/tiptap/` reutiliza
`remark-parse` + `remark-gfm` (ya en el pipeline) para leer Markdown a mdast,
y suma `remark-stringify` (dependencia nueva, la mitad que falta de remark)
para volver de mdast a texto. Esto dos funciones puras, sin estado, sin DOM:

```ts
fromMarkdown(markdown: string): TiptapDoc   // mdast → JSON de ProseMirror
toMarkdown(doc: TiptapDoc): string          // JSON de ProseMirror → mdast → texto
```

Corren igual en el servidor (para generar el documento inicial del editor) y
en el bundle de cliente (para serializar antes de guardar), porque son el
mismo módulo TypeScript importado en los dos lados — no hay dos
implementaciones que puedan divergir. Esta es además la pieza que S5 va a
extender: un bloque rico nuevo agrega su tipo de nodo a este mismo
conversor, no crea uno paralelo.

**Alcance de esta slice: sólo los nodos base del plan.** Párrafos,
encabezados, listas (con/sin orden), enlaces, código (en línea y en bloque,
con lenguaje), citas y tablas. Ningún nodo de `remark-directive` — eso es
S5, con su propio registro de bloques (`SPEC.md` §3) enganchado al mismo
conversor.

**Bundling de cliente: esbuild, servido con `@fastify/static`.** No existía
ni bundler ni servido de estáticos en el proyecto. Se agregan dos
dependencias chicas: `esbuild` (devDependency, arma un único bundle desde
`src/admin-client/editor.ts`) y `@fastify/static` (plugin oficial de
Fastify, sirve `public/admin/` bajo `/admin/static/`). Nada de esto toca el
sitio público (invariante 3): el bundle sólo se referencia desde
`views/admin/posts/*.eta`, nunca desde una vista pública. `pnpm dev` corre
esbuild en modo `--watch` en paralelo a `tsx watch`; `pnpm build` corre
`tsc` y después el bundle de cliente. El `Dockerfile` copia `public/` a la
imagen de runtime igual que ya copia `src/views`.

`tsconfig.json` suma `"DOM"` a `lib` para que `pnpm typecheck` tipe también
`src/admin-client/` (hoy sólo tipa código de servidor). No afecta al código
de servidor: ninguno de esos archivos usa APIs de DOM.

**Autosave arranca en el cuerpo, no en la creación del post.** No se toca el
esquema: `slug` y `title` siguen siendo obligatorios y únicos por espacio
desde que existe la fila (invariante que ya sostiene el `UNIQUE
(space_id, lang, slug)` de S2). En cambio, "Nuevo post" pasa a ser un paso
mínimo — espacio, título, slug, extracto opcional — que crea la fila con
`body_md` vacío (la columna ya admite cadena vacía, `NOT NULL` no es
`CHECK (length > 0)`) y redirige al editor completo. Ahí, en
`/admin/posts/{id}`, el autosave dispara desde la primera tecla que se
escribe en el cuerpo — visual o crudo — con un debounce corto (2s de
inactividad) contra un endpoint nuevo que sólo toca `body_md`/`body_html`,
nunca `slug`, `title`, `status` ni categorías. Esto es el mismo alcance que
ya tiene hoy el botón "Guardar" de S2/S3 (también reescribe `body_html` sin
mirar `status`): el autosave no introduce un riesgo nuevo de "se edita un
post publicado en caliente", sólo lo hace automático en vez de manual. Una
copia de seguridad de versiones anteriores (para deshacer un autosave
accidental) es S8 ("revisiones: histórico de `body_md` con diff") — no se
construye acá.

**Alternar visual/crudo no cambia qué se envía en el `<form>`.** El campo
`<textarea name="bodyMd">` sigue siendo el que el navegador manda en el
POST normal (sin JS no habría editor visual, pero el formulario de S2/S3
sigue funcionando igual si algo falla al cargar el bundle). TipTap se monta
sobre un contenedor aparte; el toggle sincroniza el `textarea` con
`toMarkdown(doc)` al pasar a modo crudo, y reconstruye el documento con
`fromMarkdown(textarea.value)` al volver a modo visual. El admin no está
sujeto al invariante 3 (ese es sólo para el sitio público), así que esto no
es una excepción a nada.

**Cómo se prueba el round-trip.** `tests/roundtrip/` llama directo a
`fromMarkdown`/`toMarkdown` (funciones puras, sin servidor ni navegador) con
un archivo por tipo de nodo, igual que ya anticipa la estructura del
proyecto en `CLAUDE.md`. No se agrega infraestructura de navegador (ni
Playwright ni similar) para esta slice — no hace falta un DOM real para
probar que la conversión no pierde información, y agregar esa dependencia
no lo pidió nadie. El criterio de aceptación "escribir en visual → guardar
→ reabrir en crudo" se verifica en dos capas: el round-trip prueba que el
conversor no pierde nada, y `tests/acceptance/s4.test.ts` prueba a nivel
HTTP que lo que llega por autosave/guardar se persiste y se devuelve igual
al reabrir el formulario.

## 1. Qué prueba esta slice

Del plan: que el Markdown crudo deja de ser la única forma de escribir sin
dejar de ser la fuente de verdad (invariante 1) — el editor visual y el modo
crudo son dos vistas del mismo texto, nunca dos estados que puedan
divergir. Prueba también que un bloque base (párrafo, lista, tabla, etc.)
sobrevive un viaje completo ida y vuelta sin diferencias, que es
exactamente la garantía que S5 va a necesitar para los bloques ricos.

## 2. Tareas

Cada tarea declara los archivos que puede tocar. Nada fuera de esa lista.

### T1 — Conversor Markdown ↔ documento TipTap

El núcleo, sin UI todavía. `fromMarkdown`/`toMarkdown` para los siete tipos
de nodo del plan (párrafo, encabezado, lista, enlace, código, cita, tabla),
más las marcas en línea que ya trae `remark-gfm` sobre esos nodos (negrita,
itálica, código en línea). `src/markdown/tiptap/extensions.ts` centraliza la
lista de extensiones TipTap (`StarterKit`, `Link`, `Table` + `TableRow` +
`TableHeader` + `TableCell`) que tanto el cliente (T4) como el conversor
usan como referencia de nombres de nodo — un nombre que no coincide entre
los dos lados es justo el bug que este archivo evita.

**Archivos:** `package.json` (`remark-stringify`, `@tiptap/core`,
`@tiptap/pm`, `@tiptap/starter-kit`, `@tiptap/extension-link`,
`@tiptap/extension-table`, `@tiptap/extension-table-row`,
`@tiptap/extension-table-header`, `@tiptap/extension-table-cell`),
`src/markdown/tiptap/extensions.ts` (nuevo),
`src/markdown/tiptap/fromMarkdown.ts` (nuevo),
`src/markdown/tiptap/toMarkdown.ts` (nuevo), `tsconfig.json` (suma `"DOM"`
a `lib`).

### T2 — Tests de round-trip por tipo de nodo base

Un archivo por tipo de nodo, `markdown → fromMarkdown → toMarkdown` debe
devolver el mismo Markdown de entrada (o su forma canónica, si remark
normaliza algo — por ejemplo comillas de énfasis — en cuyo caso el test fija
esa forma canónica como esperada, no la original a ciegas).

**Archivos:** `tests/roundtrip/paragraph.test.ts`,
`tests/roundtrip/heading.test.ts`, `tests/roundtrip/lists.test.ts`,
`tests/roundtrip/links.test.ts`, `tests/roundtrip/code.test.ts`,
`tests/roundtrip/blockquote.test.ts`, `tests/roundtrip/table.test.ts`
(todos nuevos).

### T3 — Bundling de cliente: esbuild + `@fastify/static`

Arma el bundle desde `src/admin-client/editor.ts` (placeholder mínimo en
esta tarea, se completa en T4) y lo sirve sólo bajo `/admin/static/`.

**Archivos:** `package.json` (`esbuild` devDependency, `@fastify/static`
dependency; scripts `dev` y `build`), `src/app.ts` (registra
`@fastify/static` apuntando a `public/admin`, prefijo `/admin/static/`),
`src/admin-client/editor.ts` (nuevo, placeholder), `.gitignore` (agrega
`public/`), `Dockerfile` (la etapa `build` corre también el bundle de
cliente; la etapa `runtime` copia `public/`).

### T4 — Editor visual montado + alternancia visual/crudo

Monta TipTap sobre el `<textarea name="bodyMd">` existente del formulario:
un contenedor visual al lado, un botón de alternar, y la sincronización
descrita en §0 para que el `textarea` real (el que el form efectivamente
envía) siempre tenga el Markdown vigente. El documento inicial (al editar
un post existente) se genera en el servidor con `fromMarkdown(post.bodyMd)`
y se embebe como JSON en la página — el cliente no vuelve a parsear
Markdown al cargar, sólo al pasar de modo crudo a modo visual.

**Archivos:** `src/admin-client/editor.ts`, `src/views/admin/posts/form.eta`,
`src/routes/admin/posts.ts` (pasa el documento inicial a la vista).

### T5 — Paso mínimo de creación de post

`/admin/posts/new` deja de pedir cuerpo: sólo espacio, título, slug y
extracto opcional. Crea la fila con `body_md` vacío y redirige a
`/admin/posts/{id}`, que ya es la pantalla de edición completa con el
editor de T4. `createPost` deja de exigir `bodyMd` no vacío en la creación
(sigue exigiéndolo — implícitamente, vía el `textarea` del form — al
guardar desde la pantalla de edición completa, donde el usuario ya está
escribiendo).

**Archivos:** `src/routes/admin/posts.ts`, `src/modules/content/posts.ts`
(`createPost` acepta `bodyMd` vacío), `src/views/admin/posts/new.eta`
(nuevo, reemplaza el uso de `form.eta` para creación),
`src/views/admin/posts/form.eta` (queda sólo para edición).

### T6 — Guardado automático de borrador

Endpoint nuevo que sólo toca `body_md`/`body_html`/`updated_at`, nunca
`slug`, `title`, `status` ni categorías (§0). El cliente lo dispara con
debounce de 2s de inactividad, tanto en modo visual (serializando con
`toMarkdown`) como en modo crudo (el valor del `textarea` directo).

**Archivos:** `src/routes/admin/posts.ts` (`POST
/admin/posts/:id/autosave`), `src/modules/content/posts.ts`
(`autosavePostBody(id, bodyMd)`), `src/admin-client/editor.ts`.

## 4. Criterio de aceptación

```text
✓ escribir un post en el editor visual, esperar el autosave, reabrir en modo
  crudo → el Markdown mostrado es limpio y equivalente a lo escrito
✓ pegar Markdown a mano en modo crudo, alternar a visual → la estructura
  (encabezados, listas, enlaces, código, citas, tablas) se ve correcta
✓ test de round-trip en verde para cada uno de los siete tipos de nodo base
✓ crear un post nuevo (paso mínimo) → autosave activo desde la primera tecla
  del cuerpo, sin requerir un "Guardar" manual antes
✓ el formulario sigue funcionando como envío normal si el bundle de cliente
  no carga (el textarea con name="bodyMd" sigue siendo el campo real)
✓ corriendo en esta máquina vía docker compose (app + caddy + postgres),
  gestionado por dockge
✓ pnpm lint && pnpm typecheck && pnpm test en verde
```
