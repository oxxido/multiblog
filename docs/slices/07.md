## 0. Decisiones tomadas para esta slice

**Dos dependencias nuevas, propuestas y confirmadas con el usuario:
`sharp` (redimensionar + codificar WebP, usa libvips precompilado, sin
tooling de sistema adicional) y `@fastify/multipart` (parsear el
`multipart/form-data` de la subida).** El stack de `CLAUDE.md` no traía nada
para esto. Son las únicas dos altas de esta slice.

**`site_settings`, tabla nueva — decidida con el usuario, no es una
extensión unilateral.** La cabecera a sangre de 520px del sitio central
(`Design.md` §2.1) asume una foto propia, pero ninguna fila del modelo la
posee: no es de un espacio ni de un post. Se agrega una tabla singleton:

```ts
export const siteSettings = pgTable("site_settings", {
  id: integer("id").primaryKey().default(1),
  coverMediaId: uuid("cover_media_id").references(() => media.id, { onDelete: "set null" }),
});
```

Una sola fila (`id = 1`), sembrada por `seed.ts` igual que espacios y
usuario. No se agrega nombre de sitio ni tagline aunque ya se esté tocando
esta tabla — ese gap lo anotó S4 aparte (`docs/STATUS.md` S4) y sigue sin
decidir; agregar columnas que esta slice no necesita es diseñar para un
hipotético, lo que `CLAUDE.md` pide no hacer.

**`spaces.cover_media_id` y `posts.cover_media_id` (ya existen desde D14)
ganan `onDelete: "set null"`.** Hoy no lo tienen: borrar una fila de `media`
referenciada como portada tira una violación de integridad referencial (un
500), justo el bug que el criterio de aceptación de esta slice ("borrar una
imagen en uso avisa y no rompe posts") pide evitar. Es una migración que
altera una restricción existente, no una que borra o renombra columnas ni
cambia una clave única — no es de las que `Db.md` pide consultar antes de
generar, pero se deja anotado acá para que no sea una sorpresa al revisar
el diff de la migración.

**Una sola fila por archivo subido en `media`; los derivados no tienen fila
propia.** `SPEC.md` §6 ya fija la forma de `media` (`filename`, `path`,
`mime`, `width`, `height`, `size`, `created_at`) y le alcanza: `width`/
`height` son los del original, y los anchos de derivado son una constante
de código, no datos. Evita una migración para lo que no la necesita.

**Disco: un directorio plano, `MEDIA_DIR` (env nueva).**

```text
{MEDIA_DIR}/
  {id}.{ext}          original, tal cual se subió
  {id}-320.webp
  {id}-640.webp
  {id}-960.webp
  {id}-1280.webp
  {id}-1920.webp       (sólo los anchos ≤ ancho original, ver abajo)
```

`MEDIA_DIR` se valida en `src/config/env.ts` igual que `BASE_DOMAIN`/
`DATABASE_URL`, con default `./data/media` para que `pnpm dev` funcione sin
configurar nada. En producción, `docker-compose.yml` monta un volumen nuevo
(`media_data`) en el contenedor `app` (sólo en `app`, `migrate` no toca
archivos) y fija `MEDIA_DIR` a esa ruta — mismo patrón que `postgres_data`
en `docker-compose.yml` hoy. `./data/` entra a `.gitignore`.

**Anchos de derivado: `[320, 640, 960, 1280, 1920]`, fijos en código, nunca
se agranda una imagen.** Cubren desde el bloque más chico (frame de
`gallery` a 4 columnas, `Design.md` §3.6) hasta una cabecera a sangre en un
monitor grande. Un original más angosto que 320px genera un único derivado
a su propio ancho (nunca upscale); en cualquier otro caso, todo ancho de la
lista que sea ≤ al ancho original genera su derivado. Es una constante de
código, no una configuración — no hay slice ni caso de uso hoy que necesite
tocarla desde afuera.

**Todos los derivados son WebP; el original se guarda tal cual pero nunca
se enlaza desde HTML.** `SPEC.md` §8 dice "media en volumen montado ... la
combinación con `pg_dump` reconstruye todo": el original se conserva por
eso (backup/exportación completa, S9), no porque el sitio lo sirva. El
`src` del `<img>` es el derivado más grande disponible; el `srcset` lista
todos. No hay `<picture>` con fallback a un formato distinto — WebP no
necesita ese respaldo hoy. Tampoco se arma `sizes`: sin ese atributo el
navegador asume 100vw, que es conservador (puede pedir un derivado más
grande del que se termina pintando) pero correcto y simple; afinar `sizes`
por contexto (640px de columna, 860px de galería, ancho completo de
cabecera) queda para si el uso real lo pide, no se construye ahora.

**MIME aceptados: `image/jpeg`, `image/png`, `image/webp`. Nada de GIF ni
SVG.** GIF perdería su animación al pasar por derivados WebP estáticos sin
que el autor lo note; SVG es código, no una foto — meterlo por esta puerta
abre una superficie de inyección que `rehype-sanitize` no cubre (un SVG no
pasa por el pipeline de Markdown). Tamaño máximo: **15 MB** por archivo,
constante de código (no env — no hay necesidad de que varíe por entorno).
Un archivo por subida; no hay carga múltiple.

**`rehype-sanitize` gana `img: ["srcset", "loading"]`.** `alt`, `width` y
`height` ya están en la lista `"*"` del esquema por defecto (verificado
contra `hast-util-sanitize`); sólo faltan estos dos, mismo patrón que S6
usó para `figure`/`figcaption`/`iframe`. `loading="lazy"` se agrega a toda
imagen con derivados, igual que S6 se lo puso al `<iframe>` de `youtube`.

**El enriquecimiento de imágenes del cuerpo es un plugin remark nuevo, no
un handler del registro de bloques.** Una imagen suelta en el cuerpo
(`![alt](/media/{id}.jpg)`) necesita `srcset`/`width`/`height` en su HTML,
pero eso exige una consulta a `media` por el id de la URL — algo que un
handler de `mdast-util-to-hast` no puede hacer (son síncronos, `(state,
node) => hast.Element`, sin await). Se agrega en cambio un plugin remark
(`src/markdown/mediaImages.ts`) que corre **antes** de `remarkRehype`,
mientras el árbol todavía es mdast:

1. recorre el árbol a mano (sin agregar `unist-util-visit` como
   dependencia — es una recorrida de `children` de ~10 líneas) buscando
   nodos `image`, incluidos los que cuelgan dentro de un
   `containerDirective` como `callout` o `gallery` — en esa etapa la
   directiva todavía no se convirtió, sus hijos son mdast común;
2. de cada `url` que matchea `/media/{uuid}...` extrae el id; si no hay
   ninguno, **no toca la base** y el resto de la conversión sigue como
   hoy — esto es lo que mantiene `tests/unit/pipeline.test.ts` corriendo
   sin Postgres, porque ninguno de sus casos referencia `/media/`;
3. con los ids encontrados hace **una sola consulta batch** a `media`
   (`width`, `height`);
4. por cada nodo `image` resuelto, escribe `node.data.hProperties` (lo que
   el handler por defecto de `mdast-util-to-hast` ya sabe volcar al
   `<img>`, sin tocar ese handler) con `srcset`/`width`/`height`/`loading`,
   **y además** `node.data.mediaImage = { width, height }` — un campo
   paralelo que sólo lee `gallery.ts` (T7), porque `gallery` arma su propio
   `<figure>` a mano y nunca pasa sus imágenes por el handler por defecto;
5. una URL que no matchea el patrón (imagen externa) o que matchea pero no
   existe en `media` (fila borrada) se deja intacta — sigue siendo un
   `<img src alt>` liso, sin romper el resto del post, mismo criterio que
   un atributo de bloque inválido en S6.

**Consecuencia arquitectónica que vale anotar: `src/markdown/pipeline.ts`
pasa a depender de la base de datos.** Hasta S6 el pipeline era puro
(markdown adentro, HTML afuera, sin I/O). Es necesario porque `SPEC.md` ya
fija que las dimensiones viven en `media`, consultada al render — y
`renderMarkdown` sigue siendo async, ya lo era desde S1. No cambia su firma
pública (`(markdown: string) => Promise<string>`), sólo dónde puede tocar
red la primera vez que un documento referencia una imagen de la
biblioteca.

**`fromMarkdown`/`toMarkdown` (TipTap, S5) no se tocan.** El enriquecimiento
es exclusivo de `renderMarkdown` (el HTML público, `body_html`); el
Markdown canónico de un post con una imagen de biblioteca sigue siendo
`![alt](/media/{id}.jpg)`, sin atributos nuevos. El round-trip `md → tiptap
→ md` de S5/S6 queda intacto porque nunca pasa por este plugin.

**`gallery` (S6) deja de aceptar sólo URLs escritas a mano: ahora inserta
imágenes elegidas de la biblioteca, y usa sus dimensiones reales.**
`gallery.ts` sigue aceptando cualquier URL externa (no depende de que la
imagen sea de la biblioteca, invariante que ya fijó S6 §0), pero cuando sí
lo es, `extractImages` lee `node.data.mediaImage` (escrito por el plugin de
arriba) y `frame()` arma `srcset`/`width`/`height` con el mismo helper
puro que usa el plugin — no una copia de la lógica.

**Integración con el editor: selector emergente con `postMessage`, no más
`window.prompt()` para imágenes.** S6 pedía URLs de galería y de YouTube por
`window.prompt()` porque no había nada más que ofrecer. Ahora que hay una
biblioteca real, un botón abre `/admin/media/picker` con `window.open()`;
al elegir una imagen (o varias, en modo galería) la ventana hace
`postMessage` a quien la abrió y se cierra sola. Sigue siendo admin puro
(invariante 3 no aplica ahí) y sigue sin modal ni framework nuevo — es una
página más, servida por el mismo `@fastify/view`, con el JS mínimo para el
`postMessage` sumado al bundle de esbuild que ya existe.

- **Botón "Imagen" (nuevo):** abre el picker en modo único; al volver, un
  sólo `window.prompt()` pide el `alt` (accesibilidad) y se inserta
  `![alt](url)` en el cuerpo — coherente con que el `alt` sigue siendo por
  uso, no por archivo (S6 §0).
- **Botón "Galería" (cambia de flujo, no de resultado):** abre el picker en
  modo múltiple (casillas + "Insertar N imágenes"); las imágenes elegidas
  entran con `alt: ""` cada una — decorativas por defecto, el autor edita
  el `alt` a mano en crudo si quiere pie de foto (S6 §0: alt vacío = sin
  `<figcaption>`). Ya no hay prompts de URL/alt por imagen: era la carencia
  que S6 §0 dejó anotada ("no hay biblioteca de medios todavía").
- **Callout y YouTube (S6):** sin cambios, siguen con `window.prompt()` —
  no son imágenes.
- **Portada (post, espacio, sitio):** mismo picker en modo único, sin
  prompt adicional — el `alt` de una portada es `""` (decorativa: el
  degradado y el texto van encima, `Design.md` §1).

**Borrar una imagen "avisa y no rompe": confirmación explícita, no un
bloqueo duro.** Antes de borrar se buscan dos tipos de uso:

1. **estructurado** — `cover_media_id` de `posts`, `spaces` y
   `site_settings` que apunten a esa fila;
2. **por texto** — `body_md LIKE '%/media/{id}%'` en `posts`, porque una
   imagen suelta en el cuerpo o dentro de un `gallery` no deja ninguna fila
   de relación, sólo la URL cruda.

Si hay algún uso, el admin muestra una pantalla de confirmación que lista
dónde ("portada del espacio X", "cuerpo del post Y") antes de borrar. Al
confirmar: se borra la fila de `media` y sus archivos en disco (original +
derivados). Los `cover_media_id` que apuntaban ahí quedan en `NULL`
(`onDelete: "set null"`, arriba) — esos posts/espacios/el sitio vuelven a
la variante "sin foto" sin ningún error. Una imagen embebida en un cuerpo
de post sí queda rota después de confirmar — el aviso ya se lo dijo al
autor; "no rompe" es sobre la aplicación (nunca un 500 por integridad
referencial), no una garantía de que el HTML de un post nunca tenga un
`<img>` roto después de un borrado que el autor confirmó a sabiendas.

**Caché larga real, no sólo mencionada en `SPEC.md`.** El `@fastify/static`
nuevo que sirve `/media/` (T5) va con `cacheControl`/`maxAge` largos e
`immutable`. Es seguro porque el nombre de archivo es estable para siempre:
volver a subir la misma foto crea una fila (y un id) nueva, nunca se
reescribe un archivo ya publicado.

**La cabecera del sitio central (`Design.md` §2.1, 520px, foto propia) es
la única de las tres cabeceras con foto (central, espacio, post) que
depende de una tabla completamente nueva (`site_settings`)** — las otras
dos ya tenían su columna desde D14. Fuera de esa diferencia de origen, las
tres se tratan igual: variante "con foto" nueva en CSS, variante "sin foto"
ya construida en S4 se mantiene intacta cuando `cover_media_id` es `NULL`.

## 1. Qué prueba esta slice

Que el modelo ya preparado por D14 (`cover_media_id` en `spaces` y `posts`)
y la promesa de `SPEC.md` §8 ("media en volumen montado, servido con
cabeceras de caché larga") funcionan de punta a punta: subir un archivo
real, que la biblioteca lo liste, usarlo como portada y dentro del cuerpo
de un post (suelto y en una `gallery`), y que el HTML público resultante
tenga `srcset`+`width`+`height`, no sólo un `<img src>` liso. Prueba también
que borrar algo en uso no puede tirar abajo la aplicación — el primer lugar
del proyecto donde una fila de una tabla puede desaparecer estando
referenciada desde otras.

## 2. Tareas

Cada tarea declara los archivos que puede tocar. Nada fuera de esa lista.

### T1 — Dependencias, esquema y configuración

Agrega `sharp` y `@fastify/multipart` a `package.json`. `site_settings`
nueva en `schema.ts`; `onDelete: "set null"` en `spaces.coverMediaId` y
`posts.coverMediaId`. Migración generada con `pnpm db:generate` (nunca
`db:push`). `MEDIA_DIR` en `env.ts`. `seed.ts` siembra la fila única de
`site_settings` (`id: 1`, `coverMediaId: null`) con el mismo patrón
`onConflictDoUpdate` que ya usa para espacios/usuario.

**Archivos:** `package.json`, `pnpm-lock.yaml`, `src/db/schema.ts`,
`src/db/migrations/` (nueva), `src/config/env.ts`, `src/db/seed.ts`,
`.gitignore` (agrega `data/`).

### T2 — Núcleo de derivados

Funciones puras y de disco, sin Fastify ni rutas todavía.
`buildResponsiveImage({ id, width, height }): { src, srcset, width, height
}` (pura, sin I/O: dado un ancho/alto original, calcula qué anchos de la
lista fija le corresponden y arma las URLs). `generateDerivatives(buffer,
id, ext)`: usa `sharp` para leer dimensiones del original, escribirlo tal
cual a `MEDIA_DIR`, y escribir un `.webp` por cada ancho aplicable;
devuelve `{ width, height }` del original. `parseMediaUrl(url): string |
null` — extrae el uuid de una URL `/media/{id}.ext`, o `null` si no
matchea.

**Archivos:** `src/modules/media/derivatives.ts` (nuevo).

### T3 — Subida, listado y borrado (módulo)

`uploadMedia(buffer, filename, mime)`: valida MIME (T0: sólo
jpeg/png/webp) y tamaño (15 MB), llama a T2, inserta la fila en `media`.
`listMedia()`, `getMedia(id)`. `findMediaUsage(id)`: junta las tres
referencias estructuradas (`spaces`, `posts`, `site_settings` por
`cover_media_id`) y la búsqueda por texto (`posts.body_md LIKE`).
`deleteMedia(id)`: borra la fila y los archivos (original + derivados) del
disco.

**Archivos:** `src/modules/media/media.ts` (nuevo).

### T4 — Rutas y vistas admin de la biblioteca

`/admin/media`: listado en miniaturas (derivado de 320) + formulario de
subida (`multipart/form-data`, un archivo). `/admin/media/:id/delete`: GET
de confirmación (usa `findMediaUsage`, lista dónde se usa si corresponde),
POST que ejecuta el borrado. `/admin/media/picker`: misma grilla que el
listado, en modo `single` (clic → `postMessage` + `close()`) o `multi`
(casillas + botón "Insertar N imágenes" → un solo `postMessage` con la
lista).

**Archivos:** `src/routes/admin/media.ts` (nuevo), `src/routes/admin/index.ts`
(registra), `src/views/admin/media/list.eta`,
`src/views/admin/media/confirm-delete.eta`, `src/views/admin/media/picker.eta`
(nuevos).

### T5 — Servir `/media/` con caché larga

Tercera instancia de `@fastify/static` (mismo patrón que la de
`/admin/static/` de S5), apuntando a `MEDIA_DIR`, prefijo `/media/`,
`decorateReply: false`, `cacheControl`/`maxAge` largos e `immutable`
(seguro: ver §0, un archivo publicado nunca se reescribe).

**Archivos:** `src/app.ts`.

### T6 — Enriquecimiento de imágenes en el pipeline público

El plugin remark descrito en §0 (`mediaImages.ts`): recorrida manual del
árbol, resolución batch contra `media`, `hProperties`/`mediaImage` por
nodo. `pipeline.ts` lo suma a la cadena, entre `remarkDirective` y
`remarkRehype`, y amplía el esquema de `rehype-sanitize` (`img: ["srcset",
"loading"]`).

**Archivos:** `src/markdown/mediaImages.ts` (nuevo), `src/markdown/pipeline.ts`.

### T7 — `gallery` usa dimensiones reales

`extractImages` lee `node.data.mediaImage` cuando el plugin de T6 lo dejó;

**Archivos:** `src/markdown/blocks/gallery.ts`.

### T8 — Portadas: post, espacio y sitio

`Design.md` §1), sin tocar la variante "sin foto".

**Archivos:** `src/routes/admin/posts.ts`, `src/routes/admin/spaces.ts`,

### T9 — Barra del editor: botón "Imagen" y "Galería" con picker

## 3. WON'T DO

Recordatorio para cualquier tarea de esta slice — no se construye nada de
esto todavía, aunque parezca dos líneas:

```text
comentarios
usuarios múltiples y roles
newsletter
analytics propio
temas intercambiables por UI
sistema de plugins
búsqueda full-text
traducciones de contenido
```

Específico de S7: recorte o edición de imagen en el navegador, carga de
varios archivos en una sola subida, carpetas/etiquetas/organización de la
biblioteca más allá de una lista, reemplazo in-place de un archivo ya
subido (subir de nuevo crea una fila nueva), CDN o servicio externo de
imágenes, GIF y SVG, `sizes` responsivo por contexto, `<picture>` con
fallback a un formato distinto de WebP, nombre de sitio o tagline en
`site_settings` (gap ya anotado en S4, sigue sin decidir), caption o alt
almacenado en `media` (el alt sigue siendo por uso, no por archivo, S6),
reordenar imágenes dentro de una `gallery` ya insertada.

## 4. Criterio de aceptación

```text
✓ subir una imagen desde /admin/media y usarla en un post (portada, cuerpo
  suelto y dentro de un gallery) desde el editor, sin tocar Markdown a mano
✓ el HTML público de las tres formas de uso incluye srcset, width y height
✓ borrar una imagen en uso muestra dónde se usa antes de confirmar, y
  confirmar no rompe el post/espacio/sitio (vuelven a "sin foto", sin 500)
✓ un archivo de MIME o tamaño inválido se rechaza al subir
✓ tests/unit/pipeline.test.ts sigue pasando sin Postgres (el plugin de
  imágenes no consulta la base si el documento no referencia /media/)
✓ corriendo en esta máquina vía docker compose (app + caddy + postgres),
  con el volumen de media nuevo montado, gestionado por dockge
✓ pnpm lint && pnpm typecheck && pnpm test en verde
```
